# Лабораторная работа 8 — юнит-тестирование

Тестируется логика курсового проекта **Velo** (прокат велосипедов).
Язык C#, фреймворк **xUnit**, покрытие считается **coverlet**.

## Запуск

```powershell
dotnet test
```

С замером покрытия и сводкой по классам:

```powershell
dotnet test --collect:"XPlat Code Coverage" --results-directory TestResults
python coverage_report.py
```

## Структура решения

```
Lab8.sln
├── Velo.Core          — тестируемая логика, вынесенная из курсового проекта
│   ├── Models.cs                 Bicycle, RentalOrder, OrderStatus
│   ├── IRentalRepository.cs      интерфейс доступа к данным — шов для изоляции

    ├── FakeRentalRepository.cs   тестовая заглушка вместо базы данных

## Почему логику пришлось вынести

В курсовом проекте юнит-тестировать было нечего. Вся логика лежала прямо
в обработчиках кнопок: расчёт стоимости, проверка дат и обращение к базе
данных соседствовали с `MessageBox.Show` и `DialogResult`. Выражение
`new AppDbContext()` встречалось в коде **22 раза** — каждый обработчик сам
создавал подключение. Интерфейсов не было вообще, то есть подменить базу
данных было физически нечем.

Поэтому логика перенесена в библиотеку `Velo.Core`, а доступ к данным
спрятан за интерфейс `IRentalRepository`. В приложении за ним стоит
реализация поверх Entity Framework, в тестах — заглушка в памяти.
**Исходный код курсового проекта при этом не изменялся.**

## Тестовая заглушка

`FakeRentalRepository` написан вручную и совмещает две роли:

- **stub** — отдаёт заранее заданные каталог и заказы, чтобы сервис
  не обращался к настоящей базе;
- **spy** — запоминает, что у него вызвали, чтобы тест мог проверить
  побочные эффекты: сохранён ли заказ и снят ли признак доступности.

Заглушка собирается цепочкой: `new FakeRentalRepository().WithBicycle(...)
.WithActiveOrder(...)`, поэтому каждый тест готовит себе ровно то состояние,
которое проверяет.

## Что проверяют тесты

Все 15 тестов построены по схеме **AAA**: подготовка данных, вызов,
сравнение с ожидаемым.

| Группа | Тесты |
|---|---|
| Расчёт стоимости | корректный расчёт на пяти наборах данных, неположительная цена, окончание не позже начала |
| Оформление аренды | сохранение заказа со статусом «создан», снятие признака доступности, аренда в прошлом, несуществующий велосипед, недоступный велосипед, пересечение периодов |
| Пересечение периодов | шесть случаев: касание границами, захват начала, захват конца, внутри, полное перекрытие |
| Регистрация | семь наборов данных, формат телефона на одиннадцати значениях |
| Пароли и рейтинг | сверка с хешем, перевод рейтинга в звёзды, выход за диапазон |

Пятнадцать методов разворачиваются в **53 тестовых случая** за счёт
параметризации через `[Theory]` и `[InlineData]`.

Отдельно стоит отметить тест `CreateOrder_ValidPeriod_MarksBicycleUnavailable`.
Он проверяет ровно тот дефект, который был найден в лабораторной работе 2:
в курсовом проекте признак доступности снимался у объекта, не отслеживаемого
контекстом Entity Framework, и до базы не доходил. В вынесенной логике этот
шаг проходит через репозиторий, и заглушка подтверждает, что вызов состоялся.

```

Непокрытыми остались шесть строк — это защитные проверки на `null`
в конструкторе `RentalService` и в `PasswordHasher`. Их тесты были убраны,
чтобы уложиться в требуемые заданием 10–15 тестов. Показательно, что отчёт
о покрытии нашёл именно эти места: по нему сразу видно, какие ветки кода
ни один тест не выполняет.

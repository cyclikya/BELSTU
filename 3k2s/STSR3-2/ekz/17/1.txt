//1. ASP.NET CORE: middleware: определение, назначение, принцип устройства, встроенные элементы. Принцип разработки пользовательского элемента. Встроенные компоненты платформы, подключаемые как middleware –элементы.

ASP.NET CORE:
    .NET Core — это платформа для разработки ПО (по сути фреймворк). Платформа = набор библиотек и инструментов для разработки. 
    Её главные свойства: кроссплатформенность и открытый код.
    .NET Core = CoreCLR + CoreFX
        - CoreFX — это библиотеки (готовый код: работа со строками, файлами, сетью и т.д.). Просто «склад готовых функций».
        - CoreCLR — это исполняющая среда, то, что запускает твою программу. Вот её надо разжевать.

    1. Назначение
    ASP.NET Core — программная платформа от Microsoft для разработки web-приложений на основе .NET Core. 
    То есть это надстройка над .NET Core именно под веб.

    2. Основные свойства
        - фреймворк с открытым кодом;
        - может работать как над .NET Core, так и над полной .NET;
        - модульность — компоненты подключаются по отдельности через NuGet, не нужна тяжёлая System.Web.dll;
        - приложения работают под IIS (Windows) или под кроссплатформенным веб-сервером Kestrel.

Middleware (промежуточное, или связующее, программное обеспечение) — это фрагмент кода в конвейере приложения, который обрабатывает запросы и ответы.

Назначение
    Разбить обработку запроса на отдельные независимые звенья, каждое из которых решает одну задачу (проверка прав, логирование, статика, обработка ошибок). Это удобно поддерживать и расширять — можно добавлять/убирать звенья, не ломая остальные.

Принцип устройства (как работает конвейер)
    Это ключевая часть. Запомни 4 факта:
    - Middleware вызываются последовательно — в порядке регистрации в конвейере. То есть в каком порядке ты их подключил, в таком они и срабатывают.
    - Каждый компонент получает контекст запроса — HttpContext (ту самую «коробку» с Request и Response).
    - Каждый middleware может:
        - выполнить действия до вызова следующего (например, залогировать запрос);
        - вызвать следующий middleware (передать запрос дальше по конвейеру);
        - выполнить действия после вызова следующего (например, залогировать ответ на обратном пути);
        - прервать конвейер и сразу вернуть ответ (дальше запрос не пойдёт).

    Это прямой аналог next() из Express: вызвал следующего — поехали дальше; не вызвал — конвейер остановился.

Встроенные middleware (готовые звенья)
    ASP.NET Core даёт много готовых middleware. Их легко узнать — все с префиксом Use:
        - UseRouting() — маршрутизация;
        - UseStaticFiles() — раздача статических файлов;
        - UseExceptionHandler() — обработка ошибок;
        - UseCors() — настройка CORS (помнишь, межсайтовые запросы?);
        и т.д.

Принцип разработки своего (пользовательского) middleware
    Если готовых не хватает, можно написать свой. По шагам:
        - Создать класс с методом Invoke или InvokeAsync, который принимает HttpContext и возвращает Task (Task — это «асинхронная задача», результат, который будет готов позже).
        - В этом методе реализовать логику обработки запроса.
        - Чтобы передать управление следующему middleware, вызвать await _next(context).




//3. Разработка клиент-серверного  приложения  с применением технологии WebAssembly на стороне сервера Node.js. 

WebAssembly (WASM) — низкоуровневый бинарный формат кода, выполняемый почти со скоростью нативного кода. 
Позволяет писать тяжёлые вычисления на быстрых языках (C, C++, Rust), компилировать в .wasm-модуль и запускать его. Не заменяет основной код, а дополняет: его функции вызываются как обычные.
Важно понимать: WebAssembly умеет работать не только в браузере. Node.js тоже умеет загружать и выполнять wasm-модули — и тогда вычисления идут на сервере.

На стороне сервера: 
модуль .wasm лежит на диске. Сервер читает его через fs.readFileSync, компилирует через WebAssembly.instantiate(буфер) и получает функцию через instance.exports.add. На HTTP-запрос клиента сервер вызывает wasm-функцию, вычисление происходит на сервере, результат возвращается клиенту.

Отличие от браузерного варианта: 
в браузере wasm грузится по сети (fetch + instantiateStreaming) и считает у клиента; 
на сервере — грузится с диска (fs.readFileSync + instantiate) и считает на сервере. 
Модуль один и тот же, меняется место выполнения и способ загрузки.»

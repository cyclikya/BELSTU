//1.	ASP.NET CORE: приложение Web API: понятие REST, назначение Web API, схема приложения, возможные реализации Web API, особенности контроллеров API. 

Понятие REST (привязка к билету 12)
    REST (Representational State Transfer) — архитектурный стиль взаимодействия компонентов распределённого приложения, где всё представляется в виде ресурсов.
    Автор — Roy Fielding (диссертация, 2000 г.).
    
    Ключевое (что нужно сказать):
        управление ресурсами через HTTP-глаголы: GET (select), POST (insert), PUT (update), DELETE (delete);
        два типа ресурса — коллекция (/api/users) и элемент (/api/users/288);
        официального стандарта нет, но REST использует стандарты HTTP, URL/URI, XML, JSON;
        RESTful — служба, полностью соблюдающая REST;
        альтернатива REST — RPC (билет 13, важно!).

Шесть обязательных ограничений REST (это спросят):
    модель клиент-сервер;
    отсутствие состояния на сервере (состояние можно хранить на клиенте или в другом сервисе, например в БД);
    кэширование на стороне клиента (сервер явно управляет кэшированием);
    единообразие интерфейсов (идентификация ресурсов через URI, манипуляция через представления, самодостаточные сообщения, HATEOAS);
    многоуровневость (для клиента сервер должен выглядеть конечным);
    код по требованию (необязательно — выгрузка на клиент скриптов/апплетов).

Назначение Web API
    Web API предназначен для создания HTTP-сервисов, которыми пользуются разные клиенты: веб-приложения, мобильные приложения, другие сервисы. Возвращает данные в формате JSON/XML через HTTP-методы.
    Главная мысль: Web API — это веб-сервис. А веб-сервис — это веб-приложение, предназначенное для работы других приложений (не для показа страниц человеку). Поэтому Web API возвращает данные, а не HTML.
    REST в ASP.NET Core реализуется именно Web API приложением (помнишь, в билете 12 это упоминали).

Схема приложения и особенности контроллеров API
    Web API основан на добавлении в MVC контроллера особого вида — контроллера API. У него две характеристики (запомни!):
        - методы действий возвращают объекты моделей, а не ActionResult (как в обычном MVC);
        - методы выбираются по HTTP-методу запроса.

    Контроллер API:
        - помечается атрибутом [ApiController];
        - наследуется от ControllerBase (а не от Controller — у ControllerBase нет поддержки представлений, она и не нужна, ведь View тут нет);
        - использует атрибуты маршрутизации ([Route], [HttpGet], [HttpPost]…);
        - данные передаются в виде моделей (DTO — Data Transfer Objects), которые сериализуются в JSON.

Возможные реализации Web API
    Это отдельный подпункт вопроса — перечисли варианты:
        - Контроллеры API (рекомендуемый, основной) — классы наследуются от ControllerBase, атрибуты маршрутизации, поддержка Model Binding и валидации, ответ в JSON по умолчанию.
        - Минимальные API (miniAPI) — для простых API/микросервисов; конечные точки прямо в Program.cs без контроллеров (билет 18).
        - gRPC — высокопроизводительная RPC-платформа; использует HTTP/2 и Protocol Buffers (Protobuf) для сериализации; хороша для связи между микросервисами; неудобна для браузера.
        - SignalR — фреймворк для реального времени; двусторонняя связь сервер↔клиент (push-уведомления) через WebSockets; для чатов, онлайн-игр, дашбордов.

Отличия Web API от MVC (часто спрашивают)
    Цель: Web API создаёт HTTP-сервисы (API), MVC — веб-приложения с интерфейсом.
    Формат ответа: Web API возвращает JSON/XML (данные), MVC — HTML (страницы).
    Контроллер: Web API наследуется от ControllerBase и возвращает модели; MVC — от Controller и возвращает ActionResult/View.




//3. Пакет Express. Основные принципы работы. Применение объекта Session для сохранение состояния. Пример (POSTMAN).

Express — это фреймворк (пакет npm) для Node.js, который упрощает создание веб-сервера. Если на голом модуле http маршрутизацию и разбор запроса приходится писать руками, то Express даёт это «из коробки».

Промежуточное ПО (Middleware) — это функции, которые имеют доступ к объекту запроса (req), объекту ответа (res) и следующей функции промежуточного ПО в цикле "запрос-ответ" приложения. Следующая функция промежуточного ПО обычно обозначается переменной next.

Основные принципы работы (по лекции):
    - Подключение и запуск. 
        Подключается через require('express'),
        создаётся приложение const app = express(), 
        запускается методом app.listen(порт). 
        Остановка — server.close().
    - Маршрутизация (routing). 
        Каждому HTTP-методу соответствует свой метод приложения: app.get(), app.post(), app.put(), app.delete(). 
        В них указывается путь и функция-обработчик. То есть маршрут = метод + путь + обработчик.
    - Объекты request и response. 
        В обработчик передаются два объекта: 
            request (запрос — со своими свойствами и методами, например req.query)
            response (ответ — методы res.send(), res.end() и др.). 
        Через них читают запрос и формируют ответ.
    - Middleware и конвейер. 
        Главный принцип Express — обработка запроса идёт через конвейер из middleware (промежуточных обработчиков). 
        Каждый middleware получает request, response и функцию next; сделав свою работу, он вызывает next(), передавая запрос следующему звену. 
        Это позволяет разбить обработку на independent модули (логирование, аутентификация и т.д.).

Применение объекта Session для сохранение состояния
    HTTP не запоминает состояние — каждый запрос для сервера как новый незнакомец. Cookie решали это, храня данные на клиенте. Session (сессия) решает ту же задачу, но хранит данные на сервере — это надёжнее и безопаснее (клиент не видит и не может подменить содержимое).
    
    Как session работает (это ключевое)
    Session использует cookie, но хитро — в этом вся суть:
        - Когда пользователь впервые обращается, сервер создаёт сессию — хранилище данных на сервере — и присваивает ей уникальный идентификатор (Session ID).
        - Этот Session ID отправляется клиенту в cookie (в Express она называется connect.sid).
        - Сами данные (имя пользователя, корзина и т.д.) лежат на сервере, а у клиента в cookie — только «номерок» (Session ID).
        - При каждом следующем запросе браузер автоматически шлёт этот Session ID, сервер по нему находит нужную сессию и «узнаёт» пользователя.

    Сравнение в одну фразу: cookie хранит сами данные на клиенте, а session хранит данные на сервере, а клиенту даёт только идентификатор (Session ID) в cookie.

    Реализация: пакет express-session подключается как middleware (app.use(session({...}))). Дальше через объект req.session: req.session.x = ... (записать), req.session.x (прочитать), req.session.destroy() (удалить, например при выходе).»

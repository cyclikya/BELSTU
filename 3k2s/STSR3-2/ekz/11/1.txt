//1. Протокол WebSocket: общие свойства, процедура handshake. 

Контекст у HTTP проблема: сервер не может сам писать клиенту, и приходилось городить polling/long-polling. WebSocket решает это по-настоящему — он даёт постоянный двусторонний канал, где и клиент, и сервер могут отправлять данные в любой момент.

WebSocket — это протокол прикладного уровня, основанный на TCP, использующий дуплексный (двусторонний) канал связи.

Общие свойства WebSocket
    - Постоянное соединение — устанавливается один раз и остаётся открытым (не нужно открывать заново на каждое сообщение).
    - Full-Duplex (полнодуплексный) — клиент и сервер могут отправлять данные одновременно.
    - Real-time — передача данных почти мгновенная.
    - Малые накладные расходы — после установки соединения HTTP-заголовки в каждом сообщении больше не шлются (в отличие от HTTP, где заголовки идут каждый раз).
    - Работает поверх TCP — использует надёжное TCP-соединение.
    - HTTP Upgrade — соединение начинается как обычный HTTP-запрос, а потом переключается на WebSocket.
    - Собственные схемы URL — ws:// (обычный) и wss:// (защищённый, по аналогии с http/https).
    - Сохранение состояния соединения — сервер «знает» подключённого клиента, пока соединение активно (в отличие от HTTP, где каждый запрос сам по себе).


Процедура handshake (рукопожатие) — вторая часть вопроса
Это то, как HTTP-соединение «превращается» в WebSocket. Происходит в три шага:
    Шаг 1. Клиент шлёт обычный HTTP-запрос (он и называется рукопожатием) со специальными заголовками:
        - Connection: Upgrade
        - Upgrade: websocket
    Этими заголовками клиент как бы говорит: «давай переключимся с HTTP на WebSocket».
    Шаг 2. Сервер решает, устанавливать WebSocket-соединение или нет. Если согласен — отправляет в ответ те же заголовки и код состояния 101 Switching Protocols (буквально «переключение протоколов»).
    Шаг 3. HTTP-соединение заменяется на WebSocket-соединение — после этого данные можно передавать в обе стороны, и заголовки на каждое сообщение больше не нужны.
Главная идея handshake: WebSocket не заменяет HTTP полностью, он начинается как HTTP-запрос и только потом «апгрейдится». Поэтому WebSocket работает на тех же портах (80/443) и проходит через ту же инфраструктуру.










//3. Пакет Express. Основные принципы работы. Выполнение shell-команд (spawn, pipe).

Express — это фреймворк (пакет npm) для Node.js, который упрощает создание веб-сервера. Если на голом модуле http маршрутизацию и разбор запроса приходится писать руками, то Express даёт это «из коробки».

Промежуточное ПО (Middleware) — это функции, которые имеют доступ к объекту запроса (req), объекту ответа (res) и следующей функции промежуточного ПО в цикле "запрос-ответ" приложения. Следующая функция промежуточного ПО обычно обозначается переменной next.

Основные принципы работы (по лекции):
    - Подключение и запуск. 
        Подключается через require('express'),
        создаётся приложение const app = express(), 
        запускается методом app.listen(порт). 
        Остановка — server.close().
    - Маршрутизация (routing). 
        Каждому HTTP-методу соответствует свой метод приложения: app.get(), app.post(), app.put(), app.delete(). 
        В них указывается путь и функция-обработчик. То есть маршрут = метод + путь + обработчик.
    - Объекты request и response. 
        В обработчик передаются два объекта: 
            request (запрос — со своими свойствами и методами, например req.query)
            response (ответ — методы res.send(), res.end() и др.). 
        Через них читают запрос и формируют ответ.
    - Middleware и конвейер. 
        Главный принцип Express — обработка запроса идёт через конвейер из middleware (промежуточных обработчиков). 
        Каждый middleware получает request, response и функцию next; сделав свою работу, он вызывает next(), передавая запрос следующему звену. 
        Это позволяет разбить обработку на independent модули (логирование, аутентификация и т.д.).



Выполнение shell-команд (spawn, pipe)
Теперь сам вопрос: как из Express-приложения запустить команду операционной системы и отдать её результат клиенту.
Модуль child_process. В Node.js за запуск внешних процессов ОС отвечает встроенный модуль child_process (по лекции — «To run a child process»). Из него берётся функция spawn.

spawn — что делает. spawn(команда, [аргументы]) запускает новый процесс операционной системы и возвращает объект дочернего процесса с тремя потоками (streams):
    stdin — поток ввода,
    stdout — поток стандартного вывода (результат команды),
    stderr — поток ошибок.
Ключевое: spawn работает потоково — данные отдаются по мере появления, не буферизуются целиком в память. Поэтому подходит для больших объёмов вывода.

pipe — что делает. pipe — это метод потока, который перенаправляет данные из читаемого потока в записываемый автоматически, кусками. В нашем случае поток вывода команды направляется прямо в HTTP-ответ:
    jschild.stdout.pipe(res);
Это значит: всё, что команда печатает в stdout, тут же уходит клиенту в ответ. (res — объект ответа — это тоже поток, в который можно писать.)

проще говоря:
«Иногда из приложения нужно запустить команду операционной системы — ту, что обычно вводят в терминале, например ls (список файлов) или echo (вывести текст).
Для этого есть встроенный модуль child_process, а в нём функция spawn. Она запускает команду как отдельный процесс. Пишется так: spawn('echo', ['Привет']) — это то же самое, как набрать echo Привет в терминале.
Результат команда выдаёт в специальный поток — stdout (стандартный вывод). Чтобы отдать этот результат клиенту, я использую метод pipe: child.stdout.pipe(res) — он переливает вывод команды прямо в ответ. То есть всё, что напечатала команда, сразу уходит клиенту.»

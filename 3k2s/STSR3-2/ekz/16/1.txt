//1. ASP.NET CORE: назначение, основные свойства, кроссплатформенность, общая структура приложения, маршрутизация, типы приложений ASP.NET CORE, программный менеджер NuGet, встроенные компоненты.  

.NET Core — это платформа для разработки ПО (по сути фреймворк). Платформа = набор библиотек и инструментов для разработки. 
Её главные свойства: кроссплатформенность и открытый код.
.NET Core = CoreCLR + CoreFX
    - CoreFX — это библиотеки (готовый код: работа со строками, файлами, сетью и т.д.). Просто «склад готовых функций».
    - CoreCLR — это исполняющая среда, то, что запускает твою программу. Вот её надо разжевать.

1. Назначение
ASP.NET Core — программная платформа от Microsoft для разработки web-приложений на основе .NET Core. 
То есть это надстройка над .NET Core именно под веб.

2. Основные свойства
    - фреймворк с открытым кодом;
    - может работать как над .NET Core, так и над полной .NET;
    - модульность — компоненты подключаются по отдельности через NuGet, не нужна тяжёлая System.Web.dll;
    - приложения работают под IIS (Windows) или под кроссплатформенным веб-сервером Kestrel.

3. Кроссплатформенность
Это главная особенность. Достигается за счёт того, что для разных ОС существуют свои версии платформы (CoreCLR + CoreFX машинозависимы и собраны под каждую ОС).
Кроссплатформенность бывает двух видов:
    - на уровне исходного кода — надо перекомпилировать под каждую ОС (пример — библиотека Qt для C++);
    - на уровне байт-кода — под каждую ОС пишут свой интерпретатор/библиотеки (например, свой CLR). 
.NET Core — это как раз второй вариант.

4. Общая структура приложения
    Общая структура приложения (OWIN + файлы проекта)
    Это, как ты правильно заметила раньше, один подпункт. У него две стороны: из чего приложение состоит логически и из каких файлов состоит проект.
    Логическая структура — технология OWIN
    OWIN (Open Web Interface for .NET) — это интерфейс между веб-сервером и серверным приложением.
    Что значит «интерфейс» здесь: это прослойка-посредник между двумя частями. Главная цель OWIN — отделить веб-сервер от приложения, чтобы их можно было разрабатывать независимо друг от друга (поменял сервер — приложение не трогаешь, и наоборот).
    По OWIN приложение состоит из 4 компонентов:
        Host — процесс операционной системы, который запускает и управляет жизненным циклом сервера (включил/выключил).
        OWIN Server — это HTTP-сервер. Его работа: побитовый (сырой) запрос от клиента превратить в удобный объект Request, а объект Response обратно превратить в побитовый ответ клиенту.
        Application — обработчик запросов (живёт в рамках одного запроса: пришёл запрос — отработал — исчез).
        Middleware — конвейер обработки запросов и ответов: подключаемые модули (помнишь конвейер из Express? Та же идея: запрос едет через цепочку обработчиков).
    Реализация OWIN-сервера от Microsoft называется Katana.

    Файлы проекта
    Те же идеи, но на уровне реальных файлов в проекте:
        Dependencies — все подключённые пакеты и библиотеки (зависимости);
        Properties → launchSettings.json — настройки запуска: адреса, порты, окружение;
        appsettings.json — файл конфигурации приложения (в формате JSON);
        appsettings.Development.json — версия конфигурации для разработки;
        [имя].csproj — файл проекта C#; ключевой кусок — атрибут Sdk="Microsoft.NET.Sdk.Web", который говорит «это веб-проект»;
        Program.cs — главный файл, точка входа; с него начинается выполнение, он настраивает и запускает приложение;
        папка wwwroot — статические файлы (картинки, css, js).
    Центральный объект — WebApplication: он настраивает всю конфигурацию приложения — маршруты, зависимости и т.д.
    Про окружения (их 3, задаются в launchSettings.json): development (разработка), stage (тестирование), product (рабочее, для пользователей). Можно писать код, который выполняется только в нужном окружении.

6. Типы приложений ASP.NET Core
ASP.NET Core позволяет делать веб-приложения разных типов (их подробно разбирают билеты 18–23, здесь просто перечисли):
    - miniAPI — минимальный API;
    - Razor Pages (Web Pages) — страницы;
    - MVC — модель-представление-контроллер;
    - Web API — для REST-сервисов.

7. NuGet
NuGet — это менеджер пакетов (диспетчер). Он занимается установкой, обновлением и удалением пакетов — то есть тех самых «кубиков»-компонентов, из которых собирается приложение. 
Именно благодаря NuGet работает модульность: подключаешь только то, что нужно. У него есть и графический интерфейс (GUI), и командный (CLI).

8. Встроенные компоненты
Это готовые возможности «из коробки», большинство подключается как middleware (звенья конвейера):

Middleware — компоненты конвейера обработки запросов (аутентификация, сжатие, статические файлы);
Dependency Injection — встроенный контейнер для управления зависимостями (билет 20);
Конфигурация — поддержка разных источников настроек (JSON, переменные окружения);
Логирование — запись логов (консоль, файлы);
Identity — система аутентификации и авторизации пользователей;
Entity Framework Core — ORM для работы с базами данных.







//3. Разработка клиент-серверного приложения  с применением технологии WebAssembly на стороне браузера. 

WebAssembly (сокращённо WASM) — это низкоуровневый бинарный формат кода, который выполняется в браузере почти со скоростью нативного кода.

Главная идея и проблема, которую он решает: в браузере единственный язык — JavaScript, но он интерпретируемый и для тяжёлых вычислений (графика, обработка видео, игры, математика) медленноват. 
WebAssembly позволяет писать такие тяжёлые части на быстрых языках (C, C++, Rust), компилировать их в бинарный .wasm-модуль и запускать прямо в браузере. JavaScript при этом никуда не девается — он вызывает функции из wasm-модуля.
Ключевые свойства:
    - бинарный формат (компактный, быстро парсится);
    - высокая скорость выполнения (близко к нативной);
    - не замена JavaScript, а дополнение — работают вместе: JS управляет, WASM считает тяжёлое;
    - кроссбраузерность — поддерживается всеми современными браузерами.



На стороне браузера: сервер отдаёт .wasm-файл как статику. В браузере 
JavaScript загружает его: WebAssembly.instantiateStreaming(fetch('/add.wasm'))
скачивает и компилирует модуль, а через instance.exports.add вызывает
экспортированную из модуля функцию. Вычисление выполняет WASM, а не JS.»

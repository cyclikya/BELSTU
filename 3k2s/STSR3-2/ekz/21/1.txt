ASP.NET CORE: приложение Razor Page: схемы работы с формами, обработка параметров формы, пересылка (upload) файлов с клиента на сервер с помощью формы. Паттерн MVVM
    Razor Pages построены на паттерне MVVM (Model-View-ViewModel) — это разделение на три части:
        View — логика представления (то, что видит пользователь, экран);
        Model — данные приложения и логика, связанная с данными (например, валидация);
        ViewModel — логика работы с данными (бизнес-логика, посредник между View и Model).

Структура приложения (View, Model, ViewModel)
    На уровне файлов:
        View — файл с разметкой, расширение .cshtml (например, Index.cshtml);
        ViewModel — файл с логикой работы страницы, .cshtml.cs (например, Index.cshtml.cs) — это «код-позади» страницы;
        Model — отдельный класс, описывающий данные.

Файл Program.cs (регистрация и подключение)
    Два шага, чтобы заработали Razor Pages:
        builder.Services.AddRazorPages();   // 1. зарегистрировать сервис
        ...
        app.MapRazorPages();                // 2. подключить
        MapRazorPages работает так: при заходе на /Имя_страницы он ищет в папке Pages страницу с таким именем и отдаёт её. Стартовая страница по умолчанию — index.

Маршрутизация
    Дополнительный адрес к странице задаётся методом AddPageRoute(pageName, route): 
    pageName — путь к странице в папке Pages, route — новый адрес. После этого при переходе по route откроется страница pageName.

Обработчики запросов (генерация ответа)
    На каждый HTTP-метод есть свой обработчик в ViewModel:
        - OnGet — на GET,
        - OnPost — на POST,
        - OnPut — на PUT, и т.д.
    Их переопределяют под нужную логику. Возвращают объект ActionResult — он описывает, что серверу сделать (вернуть страницу через Page(), перенаправить и т.д.).

Применение Dependency Injection в обработчиках
    Точно те же 4 способа, что в билете 20:
        - через конструктор ViewModel;
        - через параметр метода с [FromServices] (когда сервис нужен в одном методе);
        - через HttpContext.RequestServices (GetService<ITimeService>());
        - через директиву @inject прямо в разметке.

Razor-разметка (директивы) — компактный справочник
    Razor — движок, позволяющий вставлять C#-код в HTML. Все конструкции начинаются с символа @, после него идёт C#. На сервере Razor выполняет C# и генерирует готовый HTML. Директивы:
        - @{ ... } — блок C#-кода (выполняется на сервере, в HTML не выводится);
        - @page — превращает .cshtml в полноценную страницу с обработчиком (без неё это просто частичное представление); можно указать маршрут: @page "/custom/{id:int}";
        - @using — импорт пространств имён; либо блок с авто-освобождением ресурса (как using в C#); общие @using выносят в файл _ViewImports.cshtml;
        - @inject — внедрить сервис в представление: @inject ITimeService timeService (первый параметр — тип сервиса, второй — имя переменной);
        - @model T — указывает тип данных, переданных в представление (T — класс модели);
        - @functions { ... } — определить функции, доступные в представлении;
        - @if — условие: если истинно, отрисовать разметку в скобках;
        - @foreach — отрисовать разметку для каждого элемента коллекции (@foreach (var item in Model.items)).

Layout-макетирование (единый макет)
    Layout — единый макет для всех страниц, в который «вставляется» сама страница. Удобно для общих элементов (header, footer).
        Layout.cshtml.css — стилизация именно макета (применяется только к _Layout.cshtml);
        @RenderBody — место, куда вставляется всё содержимое страницы (что не в секциях);
        @section Name { ... } — объявить секцию с именем в странице;
        @RenderSection(name, required) — отрисовать секцию в макете; required (true/false) — обязательна ли она.
    Связь: страница объявляет @section, а макет в нужном месте вставляет её через @RenderSection.

Привязка параметров к модели (Model Binding)
    Model Binding — механизм, который автоматически достаёт данные из запроса (URL, query, форма, заголовки, тело) и сопоставляет их со свойствами C#-объектов. Делает: извлекает данные → преобразует в нужный тип → присваивает свойствам.
    Два сценария в Razor Pages:
        - Привязка к параметрам метода-обработчика — OnGet(int id): ASP.NET сам подставит id из маршрута/query (в @page "{id:int}" указываем ожидаемый тип).
        - Привязка к свойствам через [BindProperty] — основной способ для форм: свойство ViewModel помечают [BindProperty], и оно автоматически заполняется из формы при POST. После привязки запускается валидация (ModelState.IsValid) на основе атрибутов вроде [Required].

Формы, обработка параметров, upload файлов
    Схема работы с формами: Model Binding привязывает данные формы к свойствам с [BindProperty] → валидация → Post-Redirect-Get: после успешной обработки делается перенаправление (а не рендер) — чтобы при обновлении страницы форма не отправилась повторно. Если данные невалидны — страница показывается снова с ошибками.
    Upload файлов: в <form> обязательно enctype="multipart/form-data" — без него файл не отправится (помнишь это из лабы по upload!).

Tag Helpers и частичные представления
    Tag Helpers (тег-хелперы) — функциональность для генерации HTML: выглядят как обычные HTML-элементы/атрибуты (asp-for, asp-validation-for), но обрабатываются Razor на сервере и превращаются в обычный HTML. Регистрируются в _ViewImports.cshtml.
    Partial View (частичное представление) — фрагмент Razor-разметки для повторного использования, встраивается в другие представления. Способы вставки: методы Partial/PartialAsync, RenderPartial, или современный тег <partial name="..." model="..." /> (предпочтительнее — лаконичный и безопасный).





//3. Пакет Express. Основные принципы работы. Запуск процесса операционной системы (exec), работа со стандартными потоками ввода/вывода.  Пример.

Express — это фреймворк (пакет npm) для Node.js, который упрощает создание веб-сервера. Если на голом модуле http маршрутизацию и разбор запроса приходится писать руками, то Express даёт это «из коробки».

Промежуточное ПО (Middleware) — это функции, которые имеют доступ к объекту запроса (req), объекту ответа (res) и следующей функции промежуточного ПО в цикле "запрос-ответ" приложения. Следующая функция промежуточного ПО обычно обозначается переменной next.

Основные принципы работы (по лекции):
    - Подключение и запуск. 
        Подключается через require('express'),
        создаётся приложение const app = express(), 
        запускается методом app.listen(порт). 
        Остановка — server.close().
    - Маршрутизация (routing). 
        Каждому HTTP-методу соответствует свой метод приложения: app.get(), app.post(), app.put(), app.delete(). 
        В них указывается путь и функция-обработчик. То есть маршрут = метод + путь + обработчик.
    - Объекты request и response. 
        В обработчик передаются два объекта: 
            request (запрос — со своими свойствами и методами, например req.query)
            response (ответ — методы res.send(), res.end() и др.). 
        Через них читают запрос и формируют ответ.
    - Middleware и конвейер. 
        Главный принцип Express — обработка запроса идёт через конвейер из middleware (промежуточных обработчиков). 
        Каждый middleware получает request, response и функцию next; сделав свою работу, он вызывает next(), передавая запрос следующему звену. 
        Это позволяет разбить обработку на independent модули (логирование, аутентификация и т.д.).

exec — запуск команды ОС
    Как и spawn, функция exec берётся из встроенного модуля child_process и запускает команду операционной системы. Но способ получения результата у неё другой.
    exec работает через callback. Ты даёшь команду и функцию обратного вызова, в которую придёт весь результат сразу, целиком:
        exec('date', (error, stdout, stderr) => {
        res.json({ stdout, stderr });
        });

    error — ошибка запуска (если была),
    stdout — весь стандартный вывод команды (результат) одной строкой,
    stderr — весь поток ошибок.

    То есть exec дожидается, пока команда отработает полностью, складывает весь вывод в память (буферизует) и отдаёт его в callback одним куском.
    Главное отличие exec от spawn (это спросят!)
        spawn — отдаёт вывод потоком (stdout течёт кусками по мере появления). Не буферизует. Подходит для больших объёмов данных, удобно использовать с pipe.
        exec — буферизует весь вывод и отдаёт его целиком в callback. Проще, но подходит только для коротких команд с небольшим выводом.
      
Стандартные потоки ввода/вывода (stdin/stdout/stderr)
    Работа со стандартными потоками. У любого процесса есть три потока:
        - stdin — стандартный ввод (туда можно подать данные процессу),
        - stdout — стандартный вывод (оттуда читаем результат),
        - stderr — стандартный поток ошибок.

    Даже у exec можно обращаться к этим потокам напрямую. Пример: берём тело POST-запроса и подаём его на вход (stdin) команде cat (она просто возвращает то, что получила), а результат читаем из stdout:
        const child = exec('cat');
        let output = '';

        child.stdout.on('data', (chunk) => { output += chunk; });  // читаем вывод
        child.on('close', () => res.send(output));                  // когда закончил — отвечаем

        child.stdin.write(input);   // подаём данные на вход процессу
        child.stdin.end();          // закрываем ввод
    Здесь видно работу со всеми потоками: пишем в stdin, читаем из stdout.

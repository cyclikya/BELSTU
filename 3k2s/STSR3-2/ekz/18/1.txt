ASP.NET CORE:
    .NET Core — это платформа для разработки ПО (по сути фреймворк). Платформа = набор библиотек и инструментов для разработки. 
    Её главные свойства: кроссплатформенность и открытый код.
    .NET Core = CoreCLR + CoreFX
        - CoreFX — это библиотеки (готовый код: работа со строками, файлами, сетью и т.д.). Просто «склад готовых функций».
        - CoreCLR — это исполняющая среда, то, что запускает твою программу. Вот её надо разжевать.

    1. Назначение
    ASP.NET Core — программная платформа от Microsoft для разработки web-приложений на основе .NET Core. 
    То есть это надстройка над .NET Core именно под веб.

    2. Основные свойства
        - фреймворк с открытым кодом;
        - может работать как над .NET Core, так и над полной .NET;
        - модульность — компоненты подключаются по отдельности через NuGet, не нужна тяжёлая System.Web.dll;
        - приложения работают под IIS (Windows) или под кроссплатформенным веб-сервером Kestrel.

miniAPI (структура приложения)
    miniAPI (минимальный API) — это способ писать простейшие веб-приложения без контроллеров и без атрибутов вроде [HttpGet], [HttpPost]. Вместо этого:
        - используются готовые методы MapXXX (MapGet, MapPost…),
        - а логику обработки пишут прямо в лямбда-выражении (короткой функции «на месте»).
    То есть весь обработчик — это одна строчка «адрес + функция». Это самый лёгкий тип приложения ASP.NET Core (помнишь, в билете 16 перечисляли типы — вот это первый).

MapXXX и конечные точки (endpoints)
    Конечная точка (endpoint) — это HTTP-обработчик, который возвращает ответ на определённый адрес. По сути «адрес + что на нём делать».
    MapXXX — готовые методы для создания таких обработчиков. Синтаксис: MapXXX(путь, функция)
    Пример: 
        app.MapGet("/hello", () => "Привет");        // GET /hello
        app.MapPost("/products", (Product p) => ...); // POST /products
    Техн/деталь (если спросят): WebApplication автоматически добавляет в конвейер два middleware — RoutingMiddleware (в начало: находит подходящую конечную точку) и EndpointMiddleware (в конец: выполняет её).

Обработка ошибок: UseExceptionHandler и Fallback
    UseExceptionHandler — middleware, который ловит необработанные исключения, логирует их и перенаправляет на адрес ошибки (например, /error).
    Fallback-обработчик — «запасной» обработчик: срабатывает, если запрос не подошёл ни к одному MapXXX (аналог 404-заглушки).

Обработка параметров — откуда брать данные (это главное!)
    Это сердце вопроса. miniAPI умеет автоматически вытаскивать параметры из четырёх мест и подставлять их в функцию. Это называется Model binding (привязка модели) — автоматическое сопоставление данных запроса с параметрами метода.
    - Из маршрута (route) — параметр внутри URL-шаблона:
            app.MapGet("/products/{id}", (int id) => $"ID: {id}");
        {id} из адреса автоматически попадает в int id. Если тип не совпал — ошибка 400.

    - Из строки запроса (query) — то, что после ?:
            app.MapGet("/search", (string? term, int page = 1) => ...);
            // /search?term=apple&page=2
        Можно задавать значения по умолчанию (page = 1).

    - Из тела запроса (body) — для POST/PUT; JSON автоматически превращается в объект:
            app.MapPost("/products", (Product product) => ...);
        Клиент шлёт JSON → ASP.NET сам десериализует его в объект Product.

    - Из заголовков (headers) — через атрибут [FromHeader]:
            app.MapGet("/header", ([FromHeader(Name="User-Agent")] string ua) => ...);
        Атрибуты FromXXX — это явное указание, откуда брать параметр: [FromRoute], [FromQuery], [FromBody], [FromHeader]. Обычно ASP.NET угадывает сам, но этими атрибутами можно указать принудительно.

Заголовки Content-Type и Accept (связь с билетом 6)
    Content-Type — тип данных в теле запроса; ASP.NET по нему понимает, как десериализовать тело (например, JSON).
    Accept — какой формат ответа хочет клиент; miniAPI автоматически сериализует ответ в нужный формат.

MapGroup — группировка маршрутов
    Позволяет объединить несколько обработчиков под общим префиксом, чтобы не повторять его:
        var celebrities = app.MapGroup("/celebrities");
        celebrities.MapGet("/", ...);        // → /celebrities/
        celebrities.MapGet("/{id}", ...);    // → /celebrities/{id}

Фильтры конечных точек (endpoint filters)
    Это «middleware, но для одной конкретной конечной точки». Механизм для перехвата запроса/ответа на уровне отдельного endpoint.
        - реализуют интерфейс IEndpointFilter с методом InvokeAsync(context, next);
        - next — делегат вызова следующего фильтра или самой конечной точки (опять знакомый «next», как в middleware);
        - образуют цепочку: каждый фильтр может что-то сделать до и после next();
        - GetArgument — метод, которым внутри фильтра достают конкретный параметр, переданный в обработчик.

 Шаблоны и констрейнты маршрутов
    Шаблон маршрута — выражение, задающее множество URI. Например, шаблон /{id} подходит и под /1, и под /abc.
    Констрейнты (ограничения) — уточнения для шаблона, например {id:int} — только числа, {id:int:min(1)} — числа ≥ 1. Не подошло под констрейнт — маршрут не сработает.

Атрибуты FromXXX — 
    это явное указание, откуда брать параметр: [FromRoute], [FromQuery], [FromBody], [FromHeader]. Обычно ASP.NET угадывает сам, но этими атрибутами можно указать принудительно.
    это в параметрах из заголовков

Применение собственных типов в шаблонах маршрута
    По умолчанию в шаблон маршрута (/products/{id}) подставляются простые типы — число, строка. Но можно использовать и свой собственный тип (свой класс), если научить его «понимать» строку из URL.
    Как: в своём типе реализуют специальный метод TryParse — он говорит ASP.NET, как из куска URL (строки) собрать объект этого типа.
        app.MapGet("/point/{coord}", (Coordinate coord) => $"X={coord.X}, Y={coord.Y}");
    Здесь Coordinate — твой класс. Когда придёт запрос /point/3,5, ASP.NET возьмёт строку "3,5", вызовет у Coordinate метод TryParse, и тот соберёт из неё объект с X=3, Y=5.
    Суть: свой тип в маршруте работает, если в нём есть метод TryParse, который превращает строку из URL в объект.

Необязательные параметры
    Параметр, который может быть, а может отсутствовать. Два способа:
    Значение по умолчанию:
        app.MapGet("/search", (int page = 1) => $"Страница: {page}");
    Нет параметра → берётся 1. Есть (?page=5) → берётся 5.
    Знак ? (можно null):
        app.MapGet("/search", (string? term) => $"Искали: {term}");
    string? = «строка или ничего». Не передали → term будет null, ошибки нет. Без ? параметр считался бы обязательным.
    Суть: необязательный = либо значение по умолчанию (= 1), либо тип с ?.

Массивы параметров
    Когда под одним именем передают несколько значений — параметр объявляют массивом:
        app.MapGet("/products", (int[] id) => $"Выбрано: {id.Length}");
    Запрос /products?id=1&id=2&id=3 → значения соберутся в массив id = [1, 2, 3].
    Суть: повторяешь имя в query → значения складываются в массив.

Хорошо известные типы в параметрах (well-known types)
    Это специальные типы, которые miniAPI знает и подставляет сам, без привязки из URL/query. Ты просто пишешь такой тип в параметрах функции — и ASP.NET сам его передаёт. Главные:
        app.MapGet("/info", (HttpContext context, HttpRequest request, HttpResponse response) => ...);

    HttpContext — вся информация о запросе (Request + Response);
    HttpRequest — сам запрос;
    HttpResponse — ответ;
    CancellationToken — сигнал отмены запроса.

    Их не надо ниоткуда «доставать» — miniAPI распознаёт эти типы и подставляет автоматически.

Мелочи (просто знать названия)
    Валидация — проверка входных данных на корректность.
    AsParameters — атрибут, чтобы собрать несколько параметров в один объект.
    LinkGenerator — служба для генерации URL к именованным конечным точкам.
    WithName — даёт конечной точке имя; RedirectToRoute — редирект на маршрут по имени.



//3. Пакет Express. Основные принципы работы. Применение объекта Session для сохранение состояния. Пример (POSTMAN).

Express — это фреймворк (пакет npm) для Node.js, который упрощает создание веб-сервера. Если на голом модуле http маршрутизацию и разбор запроса приходится писать руками, то Express даёт это «из коробки».

Промежуточное ПО (Middleware) — это функции, которые имеют доступ к объекту запроса (req), объекту ответа (res) и следующей функции промежуточного ПО в цикле "запрос-ответ" приложения. Следующая функция промежуточного ПО обычно обозначается переменной next.

Основные принципы работы (по лекции):
    - Подключение и запуск. 
        Подключается через require('express'),
        создаётся приложение const app = express(), 
        запускается методом app.listen(порт). 
        Остановка — server.close().
    - Маршрутизация (routing). 
        Каждому HTTP-методу соответствует свой метод приложения: app.get(), app.post(), app.put(), app.delete(). 
        В них указывается путь и функция-обработчик. То есть маршрут = метод + путь + обработчик.
    - Объекты request и response. 
        В обработчик передаются два объекта: 
            request (запрос — со своими свойствами и методами, например req.query)
            response (ответ — методы res.send(), res.end() и др.). 
        Через них читают запрос и формируют ответ.
    - Middleware и конвейер. 
        Главный принцип Express — обработка запроса идёт через конвейер из middleware (промежуточных обработчиков). 
        Каждый middleware получает request, response и функцию next; сделав свою работу, он вызывает next(), передавая запрос следующему звену. 
        Это позволяет разбить обработку на independent модули (логирование, аутентификация и т.д.).

Применение объекта Session для сохранение состояния
    HTTP не запоминает состояние — каждый запрос для сервера как новый незнакомец. Cookie решали это, храня данные на клиенте. Session (сессия) решает ту же задачу, но хранит данные на сервере — это надёжнее и безопаснее (клиент не видит и не может подменить содержимое).
    
    Как session работает (это ключевое)
    Session использует cookie, но хитро — в этом вся суть:
        - Когда пользователь впервые обращается, сервер создаёт сессию — хранилище данных на сервере — и присваивает ей уникальный идентификатор (Session ID).
        - Этот Session ID отправляется клиенту в cookie (в Express она называется connect.sid).
        - Сами данные (имя пользователя, корзина и т.д.) лежат на сервере, а у клиента в cookie — только «номерок» (Session ID).
        - При каждом следующем запросе браузер автоматически шлёт этот Session ID, сервер по нему находит нужную сессию и «узнаёт» пользователя.

    Сравнение в одну фразу: cookie хранит сами данные на клиенте, а session хранит данные на сервере, а клиенту даёт только идентификатор (Session ID) в cookie.

    Реализация: пакет express-session подключается как middleware (app.use(session({...}))). Дальше через объект req.session: req.session.x = ... (записать), req.session.x (прочитать), req.session.destroy() (удалить, например при выходе).»

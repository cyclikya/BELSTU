//1. Структура HTTP-ответа.

HTTP-ответ (response) — это сообщение, которое сервер отправляет клиенту в ответ на запрос. Структура очень похожа на запрос, но с одним отличием в первой строке: вместо метода и URI там код состояния. Разберём по частям.

Из чего состоит ответ
1. Стартовая строка (status line). Первая строка ответа. Состоит из трёх элементов:
    версия протокола + код состояния + пояснение к коду
    Пример: HTTP/1.1 404 Not Found
        HTTP/1.1 — версия протокола,
        404 — код состояния (число),
        Not Found — пояснение к коду (текстовая расшифровка).
2. Заголовки (headers). Как и в запросе — пары имя: значение с метаинформацией об ответе (формат данных, длина, дата, cookie и т.д.).
3. Тело ответа (body). Сами данные, которые сервер возвращает клиенту — например, HTML-страница, JSON, картинка.

Response: Код состояния:
-	1xx: информационные сообщения;
-	2xx: успешный ответ;
-	3xx: переадресация;
-	4xx: ошибка клиента;
-	5xx: ошибка сервера.
•	100 Continue — Клиент должен продолжать отправлять запрос (например, тело POST-запроса).
•	200 OK — Запрос успешно выполнен, ответ содержит запрошенные данные.
•	201 Created — Запрос успешно выполнен, создан новый ресурс.
•	300 Multiple Choices — Запрос имеет несколько возможных ответов, клиент может выбрать один.

! Клиент отправляет запрос на сервер на доступ к ресурсу, который был перемещён. Сервер отправляет клиенту заголовок Location, в котором хранится URL, на который надо редиректнуться, а также один из статус-кодов: 301, 302, 307 или 308.
  Во-первых, 301 и 302 считаются устаревшими. В спецификации HTTP/1.1 им на замену пришли аналогичные 307 и 308.
  Вся разница в том, что 301 и 302 могли изменить метод запроса: например, делается запрос POST /api/users, возвращается 302 status code, и делается новый запрос GET /api/users. В 307 и 308 такой проблемы нет, и метод запроса всегда будет сохраняться при редиректе.
        1.	Temporary Redirect – 302 и 307
        2.  Permanent Redirect – 301 и 308 
        3.	Special Redirect - 300, 304

•	400 Bad Request — Неверный запрос, ошибка на стороне клиента (например, синтаксическая ошибка).
•	401 Unauthorized — Требуется аутентификация, доступ запрещён без авторизации.
•	404 Not Found — Запрашиваемый ресурс не найден на сервере.
•	405 Method Not Allowed — Метод запроса не разрешён для данного ресурса.
•	408 Request Timeout — Время ожидания запроса истекло, сервер закрыл соединение.
•	409 Conflict — Конфликт с текущим состоянием ресурса, запрос невозможно выполнить.
•	413 Entity Too Large — объект запроса больше, чем ограничения, определённые сервером.
•	414 URI Too Long — Запрашиваемый URI слишком длинный для обработки сервером.
•	500 Internal Server Error — Внутренняя ошибка сервера, запрос не может быть обработан.
•	501 Not Implemented — Сервер не поддерживает функциональность, необходимую для выполнения запроса.
•	502 Bad Gateway — Сервер получил неверный ответ от вышестоящего сервера.
•	505 HTTP Version Not Supported — Версия HTTP протокола, используемая в запросе, не поддерживается сервером.



//3 Протокол JSON-RPC. Разработка клиент-серверное приложение использующее протокол JSON-RPC. 

 RPC — это удалённый вызов процедур, когда клиент вызывает функцию на сервере как локальную. 
 
 JSON-RPC — это конкретный протокол RPC, в котором запрос и ответ передаются в формате JSON.

Главная идея: клиент отправляет на сервер JSON-сообщение «вызови метод X с параметрами Y», сервер выполняет соответствующую функцию и возвращает результат тоже в JSON. Обычно работает поверх HTTP (через POST).

Структура запроса JSON-RPC
    {
    "jsonrpc": "2.0",
    "method": "sum",
    "params": [1, 2, 3, 4],
    "id": 1
    }
    - jsonrpc — версия протокола («2.0»);
    - method — имя удалённой функции, которую вызываем («sum»);
    - params — параметры для функции (массив или объект);
    - id — идентификатор запроса (чтобы сопоставить ответ с запросом).

Структура ответа
    {
    "jsonrpc": "2.0",
    "result": 10,
    "id": 1
    }
    - result — результат выполнения метода;
    - id — тот же идентификатор, что был в запросе (по нему клиент понимает, на какой запрос пришёл ответ);
    - если произошла ошибка — вместо result будет поле error.

Контроллеры,   жизненный цикл контроллера,  фильтры котроллеров, применение Dependency Injection в контроллерах, обработка параметров, способы передачи данных во View.   Представление, жизненный цикл представления, применение Dependency Injection в контроллерах в представлениях, макетирование представлений, @Razor-разметка. Встроенные и пользовательские Html-helpers.  

Определение и назначение
    MVC — фреймворк для построения приложений на основе паттерна Model-View-Controller.Назначение — создавать веб-приложения, где бизнес-логика отделена от интерфейса и данных. Три слоя:
        Model (модель) — данные и бизнес-логика;
        View (представление) — отображение данных пользователю;
        Controller (контроллер) — обрабатывает запросы пользователя и связывает Model и View.
    Отличие от Razor Pages (билет 21): там логика страницы лежала рядом с разметкой (.cshtml.cs), а в MVC за обработку запросов отвечает отдельный компонент — контроллер, который сам выбирает, какое View показать.

Схема приложения (как проходит запрос)
    По шагам, что происходит при запросе:
    - запрос приходит на сервер;
    - маршрутизатор определяет, какой нужен контроллер и какое действие (action);
    - создаётся объект контроллера, он выбирает действие по HTTP-методу и параметрам;
    - происходит привязка модели (Model Binding) — данные из маршрута, query, тела;
    - вызывается действие, формируется ответ;
    - ответ записывается в HttpContext.Response, проходит через конвейер middleware и отправляется клиенту.

Маршрутизация, таблица маршрутов, шаблоны
    Маршрутизация — сопоставление URL входящего запроса с исполняемым кодом. Делает три вещи: определяет конечную точку, извлекает данные из URL (параметры), генерирует URL.Настраивается методом MapControllerRoute() с тремя параметрами:
        name — имя маршрута;
        pattern — шаблон URL;
        defaults — значения по умолчанию (какой контроллер/действие).
    Таблица маршрутизации — коллекция всех зарегистрированных маршрутов в памяти, создаётся при старте приложения. Проверка идёт последовательно, поэтому более вероятный маршрут лучше ставить в начало.
    Шаблон маршрута задаётся свойством pattern и может иметь параметры в фигурных скобках. Классический шаблон: {controller}/{action}/{id?} — система берёт из URL имя контроллера (controller), имя действия (action) и опциональный id.
    
Контроллеры
    Контроллер — центральный компонент MVC: обрабатывает HTTP-запрос, взаимодействует с моделью, выбирает View и заполняет его данными.
        создаётся наследованием от базового класса Controller (или словом «Controller» в названии);
        Action-методы (методы действий) — публичные методы контроллера, обрабатывающие запросы; обычно возвращают IActionResult;
        в базовом классе есть методы-перехватчики: OnActionExecuting() (до выполнения действия), OnActionExecuted() (после), и асинхронная версия OnActionExecutionAsync().

Жизненный цикл контроллера
    Пять этапов:
        получение запроса — маршрутизатор решает, какой контроллер использовать;
        создание контроллера — через фабрику контроллеров и рефлексию;
        выполнение действия;
        возврат ответа;
        уничтожение контроллера.
    (Рефлексия — это механизм, позволяющий находить и вызывать классы/методы по их имени во время выполнения.)

Фильтры контроллеров
    Фильтры — классы, выполняющие код до или после определённых стадий обработки запроса. Образуют конвейер фильтров. Пять типов (по порядку срабатывания):
        фильтры авторизации — проверяют, авторизован ли пользователь (если нет — обрывают запрос);
        фильтры ресурсов — выполняются после авторизации, до привязки модели;
        фильтры действий — до и после выполнения action-метода;
        фильтры исключений — обработка необработанных исключений;
        фильтры результатов — до и после формирования результата.

DI в контроллерах
    Как в билете 20: сервисы регистрируют в Program.cs (builder.Services.AddScoped<...>()), а в контроллер их внедряют через конструктор — контейнер DI сам подставит.
    
Обработка параметров
    Через Model Binding (как в билете 21) — параметры action-методов заполняются из маршрута, query, формы, тела. Атрибуты привязки: [FromRoute], [FromQuery], [FromForm], [FromBody], [FromHeader], [FromServices].

Способы передачи данных во View (это новое и спросят)
    Из контроллера в представление данные передают:
        ViewData — словарь «ключ-значение»: ViewData["Foo"];
        ViewBag — обёртка над ViewData, но через свойства: ViewBag.Foo;
        ViewModel — отдельный класс с данными, передаётся в метод View(model) (предпочтительный способ);
        через конструктор представления (данные всё равно попадают в ViewBag.Model);
        TempData — говорить только если спросят.

Представление и его жизненный цикл
    Представление (View) — компонент, отвечающий за интерфейс: HTML, CSS, JS, Razor-разметка.
    Жизненный цикл: через рефлексию ищется папка Views → папка с именем контроллера → файл с именем действия. Метод View() вызывает движок Razor (razor-engine): тот берёт .cshtml, превращает его в объект C#, методы которого заполняют Response. Объект генерируется один раз и хранится в памяти.

Макетирование и Html-helpers
    Макетирование (Layout): файл _Layout.cshtml (в папке Views/Shared), @RenderBody() — место вставки представления, @RenderSection() — именованные секции, _ViewStart.cshtml — задаёт макет по умолчанию для всех представлений.
    Html-helpers — методы для генерации HTML из C#: бывают встроенные (Html.BeginForm(), Html.TextBox()) и пользовательские (свои). Похожи на Tag Helpers из билета 21, но это вызовы C#-методов, а не теги.













//3. Пакет Express. Основные принципы работы. Выполнение js-скриптов в отдельном процессе (fork, send, worker). Пример.

Express — это фреймворк (пакет npm) для Node.js, который упрощает создание веб-сервера. Если на голом модуле http маршрутизацию и разбор запроса приходится писать руками, то Express даёт это «из коробки».

Промежуточное ПО (Middleware) — это функции, которые имеют доступ к объекту запроса (req), объекту ответа (res) и следующей функции промежуточного ПО в цикле "запрос-ответ" приложения. Следующая функция промежуточного ПО обычно обозначается переменной next.

Основные принципы работы (по лекции):
    - Подключение и запуск. 
        Подключается через require('express'),
        создаётся приложение const app = express(), 
        запускается методом app.listen(порт). 
        Остановка — server.close().
    - Маршрутизация (routing). 
        Каждому HTTP-методу соответствует свой метод приложения: app.get(), app.post(), app.put(), app.delete(). 
        В них указывается путь и функция-обработчик. То есть маршрут = метод + путь + обработчик.
    - Объекты request и response. 
        В обработчик передаются два объекта: 
            request (запрос — со своими свойствами и методами, например req.query)
            response (ответ — методы res.send(), res.end() и др.). 
        Через них читают запрос и формируют ответ.
    - Middleware и конвейер. 
        Главный принцип Express — обработка запроса идёт через конвейер из middleware (промежуточных обработчиков). 
        Каждый middleware получает request, response и функцию next; сделав свою работу, он вызывает next(), передавая запрос следующему звену. 
        Это позволяет разбить обработку на independent модули (логирование, аутентификация и т.д.).
